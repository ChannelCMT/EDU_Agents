# Agent 系统主流 7 种架构：5 章教学版定稿

## 第 1 章｜先建立选型坐标系

从零搭 Agent 系统，你是不是想到什么就让 AI 做什么？先不要急着让 AI 干活。真正要回答的是：任务有多复杂，以及你需要多强的控制力。轻任务只要快速验证，复杂任务才需要拆分、路由和状态管理。七种架构不是排行榜，而是一条从单 Agent，到协作系统，再到 Graph Workflow 的演进线。本章先记住两个判断轴：复杂度和控制力。后面每一种架构，都放回这张坐标系里选择。

## 第 2 章｜单 Agent 与 ReAct：从能跑到会探索

单 Agent 就是一个大模型包揽输入、思考、调用工具和输出。它简单、便宜、延迟低，适合做概念验证和简单对话；一旦任务变复杂，模型容易认知过载，出现上下文污染。ReAct 把过程变成 Reason 加 Action 的循环：思考、行动、观察，再决定下一步。它比单 Agent 更适合多步探索，也更容易解释过程，但 Token 消耗大、容易跑偏，不适合直接承担大规模生产流程。

## 第 3 章｜Plan and Execute 与 Multi-Agent：把复杂任务拆开

Plan and Execute 先生成完整计划，再按步骤执行。它让流程更稳定，适合代码生成和长流程自动化；但计划如果一开始就错，后面的执行会把错误放大，灵活性也不如 ReAct。Multi-Agent 再进一步，把任务分给不同角色，例如 Planner、Executor 和 Reviewer。这样上下文边界更清楚，复杂流程更容易扩展，代价是调用成本、协作协议和失败处理都会增加。它适合对流程一致性要求高的行业任务。

## 第 4 章｜Route+Skill 与 Blackboard：让系统可控、可协作

Route+Skill 的关键不是让模型自由发挥，而是先让意图路由器选中一个 Skill，再执行这项可复用能力。这样更稳定、更容易缓存，也能用命中率评估效果；代价是 Skill 设计成本高，还要处理路由冲突。Blackboard 则让多个 Agent 共同读写一份共享状态，状态变化推动下一步执行。它适合复杂协作，但状态模型、权限和追踪必须先设计好，否则出了问题很难定位。

## 第 5 章｜Graph Workflow：把选型落到生产环境

Graph Workflow 用图来编排长流程：节点代表步骤，边代表条件；它可以支持分支、并行、回溯和重试，所以最适合流程自动化和生产环境。你可以把七种架构排成一条演进线：单 Agent 做最小验证，ReAct 做多步探索，Plan and Execute 做工程化，多 Agent 做角色协作，Route+Skill 做精准技能系统，Blackboard 管共享状态，Graph Workflow 承载长流程。最后用三问做选择：任务有多复杂？哪里必须可控？失败后能不能重试和回滚？没有最好的架构，只有最合适的架构。
