# 从原始素材到课程视频：端到端制作流程

这份流程面向需要持续生产课程视频的团队。目标不是一次做出“看起来不错”的动画，而是让每一步都有输入、产物、审核点和失败处理，换一个主题也能复用。

## 0. 先定义完成标准

开始前先回答：

- 给谁看：企业家、大学生、团队内部，还是公众科普？
- 看完能做什么：理解概念、完成操作，还是交付一个作品？
- 发布到哪里：抖音、小红书、视频号、B 站或课程平台？
- 是否需要数字人、横竖封面、字幕、配套 PPT 或 GitHub 教材？
- 哪些素材允许公开，哪些只在本地使用？

完成标准至少包括：章节数、目标时长、视觉风格、声音、字幕、封面、发布文案和审核人。

## 1. 原始素材与转录

### 输入

- 原始视频、音频、访谈、文章、已有 PPT；
- 参考视频的内容结构和动画风格；
- 目标受众、平台和时长。

### 操作

1. 建素材清单：文件、来源、用途、版权、是否公开。
2. 对音视频做转录，保留源时间码。
3. 人工校正专有名词、英文、数字和逻辑分段。
4. 建 `terminology.yaml`，锁定屏幕拼写、口播读法和 ASR 常见误识别。

### 输出与验收

- `asset-inventory.yaml`
- `canonical-transcript.md`
- `source-timecodes.yaml`
- `terminology.yaml`

验收：原始信息没有漏段，术语只有一个批准写法，公开仓库不含未授权媒体。

## 2. 从原稿改成课程讲稿

原稿适合“被采访”或“被阅读”，不一定适合“被讲授”。改写时先拆教学任务，再写口播。

### 五章常用结构

1. 场景问题：为什么这个问题值得解决？
2. 概念边界：几个相似概念分别解决什么？
3. 核心系统：它如何运行？
4. 约束与证据：怎样避免失败？
5. 落地任务：学习者下一步做什么？

### 讲稿规则

- 一段只表达一个主要结论；
- 先给问题或对照，再给定义；
- 口播用自然短句，不照读 PPT；
- 英文术语第一次出现时给中文解释；
- 案例数字写明边界，不变成普遍效率承诺；
- 把“更好、更规范”改成可检查要求。

每章输出唯一、版本化的 `SCRIPT.md`，由内容负责人确认后再进入配音。

## 3. 语气规划师

语气规划不是添加“激昂、专业”两个形容词，而是把讲稿变成可执行的声音导演表。

每个段落需要记录：

- `intent`：提问、解释、对照、警示、收束；
- `energy_curve`：起、承、转、落；
- `pace`：正常、稍慢、加快；
- `pause_before/after`：停顿秒数；
- `emphasis`：需要落重音的词；
- `breath_points`：自然换气点；
- `pronunciation`：英文和数字的读法；
- `caption_break_hints`：可用作字幕断句的语义停顿。

英文词出错时，先改术语读音和局部语气，再重做最小句段。默认不把同一句拆成两条声线拼接，因为声纹、速度和连接处容易不自然。

## 4. Fish Audio 配音

1. 按语义段生成音频，避免整章失败后全部重做。
2. 使用批准的公开声线标签；真实 Voice ID 从环境变量读取，不写进公开仓库。
3. 记录每段脚本版本、顺序、时长、文件校验值和状态。
4. 人工检查普通话、英文、呼吸、停顿、速度和整体一致性。
5. 冻结最终音频；之后所有动画和字幕时间以它为准。

这一步的输出是 `voice-manifest.yaml`、`audio_meta.json` 和最终分段/合并音轨。

## 5. 逐词对齐

ASR 只负责提供实际时间，术语文字以批准脚本为准。对齐时重点人工复核：

- 英文术语；
- 数字、缩写和产品名；
- “但是、再、最后”等转折；
- 动作词：打开、修改、测试、提交、验收；
- 需要出现新卡片或切换状态的短语。

没有这份真实时间表，不允许锁定动画秒数。

## 6. 语义锚点和分镜映射

先建立不带秒数的锚点计划，再把词级时间填进去：

| 类型 | 说明 | 视觉要求 |
|---|---|---|
| `segment` | 一段开始 | 句首 0.12 秒内有承接动作 |
| `term` | 术语、数字、关键名词 | 约提前 0.10 秒可读 |
| `action` | 执行动作 | 对应一次可见状态变化 |
| `turn` | 但是、再、最后 | 先切状态，再进入下一组 |

每个锚点只对应一个主要视觉对象。后面的概念不得因为“这一页最终都要出现”而提前展示。

## 7. 15–20 秒对齐试片

选择全章最难的一段，不一定选开头。通常优先：

- 英文术语密集段；
- 多节点依次出现的流程；
- 从一个概念切到另一个概念的转折；
- 箭头和状态反馈较多的片段。

试片通过后再扩展整章。同一段失败时，先修 `word-alignment` 或 `semantic-timing-manifest`，不要一开始随机挪动画或补页面时长。

## 8. 深蓝浅蓝 PPT 风格动画

默认视觉：深蓝底、浅蓝高亮、白字、浅灰辅助、少量黄色重点。先画安全区，再放元素。

- 主标题 ≥54px；
- 正文 ≥24px；
- 关键卡片/节点名 ≥26px；
- 一页一个主结构，辅助卡不超过三张；
- 网格小而淡，不抢内容；
- 字幕区 `y=900..1080` 不放关键内容；
- 箭头方向表达真实因果或顺序，不只做装饰。

数字人只在章节开头或结尾短暂出现，默认 3–8 秒。外部对嘴视频接入前检查音轨，避免和 Fish Audio 叠成两份声音。

## 9. 双门禁与逐章渲染

### 布局门禁

检查文本溢出、图层重叠、卡片越界、箭头穿卡、标题过密和字幕安全区。

### 语义门禁

逐段回答：听到什么、看到什么、何时出现、停留多久、何时退出。视觉进入窗口为语义词前 0.15 秒至后 0.12 秒；与当前语义相关的画面变化不能静止超过 1.4 秒。

先渲染每章无字幕版，人工批准后再进入字幕和合并。

## 10. 字幕与合并

字幕从最终视频音频重新获取词级时间。断句优先级：语气停顿 → 完整语义 → 自然词组 → 14 字上限。

- 字幕与语音词序一致；
- 一行 5–14 个可见字；
- 不拆英文词，不留下缺宾语短语；
- 目标比声音提前 0.05 秒；
- 词级误差 ≤80ms；
- 52px 白色粗体，最低 48px；
- 深蓝半透明图层，底下 PPT 仍可辨认。

合并后检查章节顺序、总时长、H.264/AAC 和唯一人声音轨。

## 11. 封面、文案与发布包

同时输出横版 4:3、竖版 3:4。标题、图形、CTA、边框各自有安全区，检查真实发光/阴影/描边包围盒。发布包包含：

- 最终 MP4；
- 两张封面；
- 标题、短描述、正文、标签、置顶评论；
- `final-media-report.json`；
- `release-manifest.yaml`。

## 12. 发布反馈写回 Harness

反馈不能只记录成“下次注意”。要转成数字或可判定条件，例如：

- “手机上字太小” → 标题/正文最小字号 + 50% 缩放预览；
- “字幕挡画面” → 固定字幕安全带 + 动画中间帧检查；
- “字幕像实心块” → RGBA 半透明承载层 + 底图可辨认检查；
- “嘴型视频声音重叠” → 外部 MP4 音轨检查 + 最终单人声门禁。

## 13. 五章并行与合并

共享真相冻结后再并行：讲稿、术语、语气规划、最终音频、词级对齐、视觉规范和第 1 章试片属于串行门禁。第 1 章试片通过后，Chapter 1–5 可以各自执行动画、渲染和字幕，推荐最多并发 3 章；每个工作单元只写自己的 `chapter-XX/**`。

所有章节字幕门禁通过后才进入合并。合并、媒体流检查、发布批准保持串行。封面和发布文案可以在讲稿冻结后并行起草，但不得提前冻结最终发布包。

并行执行以 `workflow/course-video-workflow.yaml` 的 `parallel_execution` 为准，失败时只回滚失败章节或失败句段。
